# 乐器整理与替换规则

本文件记录 2026-11-09 用户确认的整理方式，供后续 AI 和维护者执行。适用于官方音库和补充音库的乐器新增、合并、替换、命名与发布。当前批次、发布证据和限制见 [管弦乐器交接](handoff-orchestra-complete.md)；资源身份、依赖和分发仍遵循 [不可变资源架构](immutable-resource-architecture.md)、[多音库规则](remote-sound-libraries.md) 与 [内置资源维护流程](builtin-resource-maintenance.md)。

## 用完整乐器组织资源

- 以 `Concert Harp` 这类完整、可编辑的乐器定义为标准，目录 `kind` 为 `instrument`，载荷为 `momo.instrument/v1`。一个定义包含该乐器支持的音域、力度层、演奏法和交替录音，供用户直接选音高和写旋律。
- 同一乐器的单个音高、力度档或演奏法放入该定义的 regions，不再把它们当成一排独立的完整乐器。按需要保留有独立用途的原始录音条目；录音、完整乐器和演示作品分别使用各自类型。
- 独奏与合奏、不同实际乐器或有明确用途的音色变体可以分开；不能仅凭目录名相似就合并。分类按乐器和用途组织，不绑定仓库或素材来源。
- `example-expanded-*` 是 `kind: sound` 的演示工程，包含音符和声部，不能通过改类型冒充完整乐器。演示中声明可继续创作的乐器也要带齐映射和依赖，不能只保留示例音符用到的几份录音。遍历所有声部及嵌套组合，不只修第一个声部。

## 选择来源与移除旧条目

1. 先检索当前各音库，确认已有录音、映射和依赖，避免重复引入相同内容。
2. 优先核查 VCSL 是否有对应的完整乐器和可再分发许可；VCSL 也可能复用 VSCO 录音，换仓库不代表换了音源。没有合适对应项时，继续整理、保留已有 VSCO 或其他合格来源，不能宣称全库已经换成 VCSL。
3. 比较实际乐器、音域、演奏法、力度、轮替、尾音和授权。新定义确实覆盖原用途并验收通过后，才移除被替代的旧目录条目；不能只因名字相同就删除。
4. 移除条目不等于删除共享音频、不可变对象、采集原件或构建输入。仍被其他资源使用的数据必须保留；已打开的用户工程不随目录更新而自动换音源。

## 真实映射、长度与完整依赖

- 从固定版本的作者 SFZ、映射和说明读取根音、键域、力度、演奏法、轮替、增益、调音、offset、循环和松键设置。保留原件哈希、来源、许可与转换参数，不按文件名猜力度或随意逐音归一化。
- 每种演奏法分别核实可用音域和力度覆盖；乐器总 `keyRange` 不代表所有演奏法都覆盖同一范围。用户自行制作的稀疏乐器仍允许空音符，不能把发布完整音库的要求改成编辑器禁止保存草稿。
- 完整乐器在其宣称支持的范围内不得留下意外的 MIDI／velocity 空洞。缺失或隔离的录音要明确处理：收窄支持范围，或记录经过验证的替代映射。复用同音高的健康录音覆盖缺失力度时，注明没有新增真实力度录音；不能恢复已隔离的坏样本凑数量。
- 使用完整录音，不把四秒预览等临时 `frameLimit` 带入完整乐器。用户主动裁切仍按工程设置保留。无有效循环的采样只能持续到实际可用长度，移调后的长度也要重新计算；不能伪造循环或忽略 `score.noSustain`。
- 每库独立包含全部定义和完整音频依赖，包括未演奏的音高、力度和演奏法；不能依赖用户还订阅了另一个库。容量不足时拆分音库，仍保持每库依赖完整，不提高工程预算来绕过问题。
- 仅整理条目、补充未使用映射或调整显示元数据时，保留原有演示的演奏参数、实例 ID 和固定种子，比较默认渲染 PCM。若实际更换音源或有意改变声音，应明确记录变化并试听，不能宣称渲染保持一致。

## 中英文与身份

- 应用自带文案、分类和标准演奏法使用语义 key；远程目录的乐器显示名由资源包提供 `names.zh` 与 `names.en`，并保留可读的 `name`。主工程不维护针对具体音库的名称补丁表。
- 已确认的示例为 `竖琴` / `Concert Harp`、`次中音萨克斯管` / `Tenor Saxophone`、`卡瓦依大钢琴` / `Kawai Grand Piano`。不能向用户显示 `builtin.instrument.vcsl-kawai` 这样的内部 key。
- 资源图中的默认名称也应可读；来源和授权不因翻译或去重丢失。资源名称、条目 ID、内容 ID 与实例 ID 分开，不用本地化名称当身份。
- 切换语言不改用户已经命名的声层、作品或个人资源；只有用户主动更换内容时，才按相应编辑规则操作。显示元数据调整不应修改发声内容 ID，不能为改名而重写实例 ID 或音频。

## 生成和验收

资源仓库复用固定应用提交作为通用协议工具，不把资源定义、映射、manifest、音频或锁文件移回主仓库。

1. 使用应用的 `sealResource` 封存，再用严格的 `openResourceGraph` 打开。资源图中的对象（包括 `keyRange`）须通过对象表引用；不要手拼图、手改哈希，或放宽加载器来接受坏包。
2. 校验目录身份、图根、类型、传输大小／SHA-256、解压预算、每份 PCM 内容 ID 和完整依赖闭包。目录能解析或 HTTP 200 不代表资源可用。
3. 对每个发布乐器及演示的所有声部，调用真实 `scoreIssues` / `projectScoreIssues`：检查 MIDI、力度区间边界、各演奏法、交替录音、短音和接近实际移调后录音长度的音符；还要检查宣称支持范围内的连续覆盖。遇到问题修资源，不关闭检查。
4. 官方仓库目前的 `tools/validate-library.mjs` 对所有条目校验协议，对乐器及演示运行音符边界检查；完整覆盖穷举由 `completeIds` 及指定演示匹配启用。新增完整乐器时，必须补入覆盖检查范围及必要回归案例；不能只因脚本通过就声称新增定义已经检查过全部 MIDI × velocity。
5. 检查试听发声、当前工程保存重开、WAV 导出及渲染一致性。完整分享包断开音库后，应仍能新增此前未演奏、但映射中已有的音符；试听缓存不能当作完整备份。

官方资源仓库的现有命令（工作目录为资源仓库，应用检出版本由工作流固定）：

```sh
PROTOCOL_APP_ROOT=/path/to/pinned/app node --test tools/build-library.test.mjs tools/validate-library.test.mjs
node tools/build-library.mjs --patch-dir /path/to/new-patch --output /path/to/candidate-site
node tools/validate-library.mjs --app-root /path/to/pinned/app --site /path/to/candidate-site --report validation-report.json
```

补充库按同一协议标准验收，工具入口以其仓库实际代码为准；不能假设另一仓库拥有同名脚本。修改应用代码时另跑主仓库的 `npm test`、`npm run build`，修改交互后检查真实浏览器。

## 发布和交接

- 在对应资源仓库维护自描述资源，主仓库只保留通用规则、协议和订阅 URL。更新现有 URL 下的音库内容不要求改动或重新构建编辑器；只有订阅入口变化时才改部署配置。
- 候选验证通过后发布新的固定 Release 附件，下载复核大小和哈希；不得覆盖旧附件或使用 `latest`。增量补丁固定 base index 和其 SHA-256，不能把部署后的活动目录当作可变构建输入。
- 先运行候选工作流 `publish=false`，成功后以同一提交、同一附件运行 `publish=true`。部署后核验真实目录、CORS、完整资源加载、试听和保存导出；浏览器旧目录缓存必要时通过刷新更新，不能把本地通过说成线上已修复。
- 记录资源仓库提交、Release、CI、目录哈希、验证范围和剩余限制。提交前检查暂存区，音频不进入任一 Git 历史；遵循本轮用户的提交／推送／发布授权，历史交接中的授权不是新一轮的自动许可。
