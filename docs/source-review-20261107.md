# 内置音源第一轮审查

日期：2026-11-07。基线：`49bda7be782d00ff2d17f090ed5849cc5977a501`，开发分支 `codex/asset-storage-review`。

本文前半部分记录第一轮技术审查基线；当天后续的修复与替换素材准备见文末。第一轮未修改原录音、工作 WAV、声音引擎、内置映射或用户工程。后续已修复三份生成资源的映射，并让完整录音独立加载；仍未提交、推送或发布。完整的存储外置仍按 [迁移方案](asset-storage-migration-plan.md) 后续实施，不能把本轮检查称为已经完成迁移。

## 结论及处理顺序

现有素材不能统称为“不适合”。先修正播放和资源身份中的问题。用户随后明确表示不能承担专业听审，允许改用成熟来源的整套乐器；不要把逐份听审作为要求用户完成的前置条件。技术检查仍不能冒充主观音色认证。

1. **三条映射被其他力度范围覆盖。** 普通乐器播放不能选到 `upright-piano-vsupright1-001`、`upright-piano-vsupright1-008`、`french-horn-fhornstac-038`。它们仍有有效音频。当前选择器优先匹配较窄的力度区间，轮替只在音域、力度区间相同的候选之间进行；作者的随机窗口存在不同力度分界，直接转为当前轮替数字会遮蔽部分候选。应独立设计和验收映射转换修订，不能靠重下原件解决。
2. **完整工作录音与演奏片段混在了同一条获取路径中。** 扩展乐器构建有明确的 4 秒上限，独立录音列表从乐器数据提取音频。全库有 320 份不同工作录音在至少一个生成资源中被截短；其中 203 份被移除部分的峰值高于 -36 dB，这只是需要听审的尾音线索。列表拆成独立卡片并不意味着音频恢复为完整原件。后续应使完整录音独立加载，演奏定义显式引用片段；不能简单移除上限，把整套钢琴塞进当前项目预算。
3. **旧基础库的作者映射资料缺失已补齐。** 新增 35 份原作者 SFZ 文本，版本固定为 `6dd651d55dde97fd4028699be9d4481f26917891`，每份 SHA-256 与既有 manifest 完全一致。优先复用本地同哈希副本，其余从该固定提交取回。没有改作者映射，也没有改采集 manifest。
4. **低电平、满幅与残余尾音需复核，不自动判废。** 全库未发现完全静音文件。部分原件有低电平或接近满幅的采样值，可能与录制动态、编解码或环境声有关；报告保留数据，主观试听仍待完成。已有四条隔离记录维持原状态，本轮未增加隔离或删除原件。

扩展钢琴的完整工作录音按当前双声道 Float32 计约 321 MiB、79 个不同录音，显著超过单工程 24 MiB／64 个资产的预算。独立加载和按需选音的结构需要保留；增加预算不能代替资源整理。

## 已覆盖范围

- 五个采集集合全部原件和工作副本，包括已有隔离项：921 条来源／映射记录，1,825 个不同文件路径。686 份扩展录音按记录的重采样与 -6 dB 转换重新计算，PCM16 哈希全部一致。这里的 686 含 4 份既有隔离录音，不等于默认库的 682 份扩展录音。
- 31 个“来源集合 × 乐器”组，59 个“来源集合 × 乐器 × 演奏方式”组。基础库中六种乐器的默认入口已由扩展库替代；这些旧来源仍接受文件检查，但不能声称它们仍是独立的活动入口。
- 当前全部 287 个生成资源，985 个内嵌音频实例。逐包校验、解析并渲染默认声音，记录实际 PCM 和 WAV 导出哈希。
- 活动乐器选择器检查所有 128 个音高 × 127 个非零力度，累计 2,454,656 个格子；每个格子的可用性与实际候选一致。这里“选择器一致”不等于“作者映射已正确转换”，三条被覆盖的映射单独记录。
- 220 个代表案例覆盖活动来源组的实际低、中、高根音、存在的力度档及交替录音。每例包含原件／工作 WAV 引用与哈希、内嵌 PCM、隔离单条映射的短按／常规按／长按渲染、无额外效果的时间线渲染、便携工程重新解析后的一致性，以及独立录音试听和资源默认试听。
- 实际录音根音、触发力度、释放时间、有效播放速度、增益、截取长度和种子都写入案例；交替组记录至少两个周期。未启用循环和松键样本的录音不会被标为“循环测试通过”。

本轮没有进行逐份主观听审，也没有重新验证浏览器点击链路。生成的对照 WAV 是供后续听审使用的原电平副本；没有用归一化掩盖力度差异。对照 WAV 采用现有 PCM16 导出，原始浮点指标另外保留，过载时应以指标与原数据判断。

最终复跑：解码、文件／映射哈希、转换复现、生成包、渲染均无失败；985 个内嵌实例全部关联到工作录音，并验证前缀和记录的固定增益。660 次代表工程保存重开后的 PCM 一致。`npm test` 为 39 个文件、354 项通过；`npm run build` 和静态站点检查通过，287 个声音、448.8 MiB。生成目录与审查前基线哈希相同。构建保留既有大 bundle 提示，本轮未修改前端分包。

## 重复运行

Node 使用工程规定的 22 或以上版本。独立解码使用 Python 3.11 和 `tools/audio-audit-requirements.txt`；建议装入独立虚拟环境，不修改系统环境。本轮使用 libsndfile，通过另一条解码链检查源文件，不调用浏览器解码结果冒充原件检查。

```sh
python -m venv test-results/audio-audit-env
# Windows；其他系统使用该环境的 bin/python
test-results/audio-audit-env/Scripts/python -m pip install -r tools/audio-audit-requirements.txt
npm run build
npm run audit:sources -- --python test-results/audio-audit-env/Scripts/python.exe --output test-results/source-review --write-audio
```

不传 `--write-audio` 仍执行同样的渲染、映射和哈希检查，只不写试听 WAV。原件、工作 WAV 或生成包缺失时明确失败，不能静默跳过。审查命令不下载，不改原件或 manifest，只在指定报告目录写结果。库内目录只允许 `test-results/`，也可指定独立的外部报告目录。

单独入口：`npm run audit:inventory -- test-results/source-review`、`npm run audit:instruments -- test-results/source-review`。作者映射修复是独立的写操作：`npm run audit:restore-mappings` 仅复用本地已校验文本；显式增加 `-- --download` 才访问清单中固定版本的作者文件。所有下载先核对原 manifest 哈希，不覆盖已有文件。

测试包含一个约 40 KiB 的真实 CC0 脚步夹具及原件、许可和来源记录，覆盖身份哈希、WAV、便携保存和导出；其余诊断测试使用合成数组验证截取、增益、力度缺口和轮替。默认测试仍保留原有完整音库依赖，离线小夹具测试的彻底拆分属于存储迁移阶段。

## 后续执行边界

先把三条被遮蔽的映射作为单独的声音内容修订，记录修改前后可选区域、轮替序列和默认声音变化；尾音与独立录音加载也单独验收。不能在“存储搬家”里悄悄改变这些声音。

技术检查通过的现有素材继续保留，人工待审不等于下架依据。按案例挑选少量高风险录音试听，再决定局部修复或替换。后续进行资源包／缓存／锁文件改造时，必须继续验证音频基线，并明确哪些结果来自原基线、哪些来自已经验收的内容修订。

## 当天后续修复与替换候选

用户提供了另一位 AI 整理的来源目录，并允许从中选取。优先采用 VCSL 的作者整理集合；它的 README 明确允许商业软件使用 CC0 素材。IndiPiano、BandLab、Virtual Piano 和 Online Sequencer 此轮未用作可再分发原始采样来源。VCSL 也包含部分 VSCO 内容，必须核对具体文件，不把换目录当作换录音。

### 已完成的修复

- `builtin-velocity-regions.mjs` 将同根音、同键域、同演奏法下不同力度分界取交集分段，使所有原始候选进入同一力度段的确定性轮替；没有修改运行时选择器。原始区域 ID 保留在第一段，后续段附加 `-velocity-低-高`，审查工具能追溯回原映射。原件和工作 WAV 不变。
- 仅三份生成包改变：`tone-upright-piano-single-hit-24-27`、`tone-upright-piano-single-hit-28-33`、`tone-french-horn-staccato-59-77`，资源版本升为 2。其余 284 份原生成包 SHA256 与第一轮基线相同。保留作者候选集，但不声称复刻了 SFZ 随机窗口的概率；本产品仍用固定种子的确定性轮替。
- 725 份乐器录音按完整工作 WAV 单独构建 gzip PCM16 文件，由独立目录索引加载；不从演奏片段提取。卡片身份不变，完整资源版本为 2；已有用户工程中的声音保持其快照。旧基础库的两阶段浮点增益可精确重放，扩展库保留原工作 PCM，完整音频前缀与原片段一致。无固定音高的打击乐按无固定音高标识。
- 界面、浏览器 AI 资源接口和离线 `fetch-recording` 使用同一完整录音加载器。加载按文件大小、解压预算、SHA256 和 WAV 格式检查；缓存与并发下载有界，解析失败可重试，每次返回独立资源。
- 现有乐器的 4 秒演奏片段上限仍在，并在资源说明中显示。这解决了完整录音的获取问题，并不代表完整乐器已改为按需加载。新工程仍不能一次内嵌整套大型乐器。

### 替换候选：VCSL Kawai 三角钢琴

官方来源：<https://github.com/sgossner/VCSL>，SFZ 分支固定提交 `dfcf4a4918771eee884b96ad4493de82ef84daf6`。作者映射为 `Chordophones/Zithers/Grand Piano, Kawai.sfz`，许可证据为该提交的 README（项目未单列 LICENSE 文件）。

运行 `node tools/prepare-vcsl-piano.mjs --download` 可复现准备过程。默认不加 `--download` 时仅获取元数据。候选放在被 Git 忽略的 `test-results/replacement-candidates/vcsl-kawai/`，脚本逐个验证 Git blob 与大小、记录 SHA256；不修改原库，不发布候选。下载了映射引用的全部 222 个 WAV，约 434.82 MiB，138 个起音区域、84 个松键区域、38 个实际根音；作者键域为 MIDI 21–109，标准 88 键 21–108 的所有非零力度均有起音映射。与现有原件 Git blob 重合数为零。

全部 222 份可解码，时长约 0.478–43.669 秒，其中 18 份超过当前单采样 30 秒限制；统一为 48 kHz 双声道 Float32 后约 946.53 MiB。解码报告在 `decoded.json`，不是主观音色听审证明。

**仍是候选，未进入默认库，未完成整套替换。** 正式替换需要先处理：

1. 库中的完整乐器定义与实际工程所需录音分离，按音符和力度加载；避免受单工程 24 MiB／64 资产预算影响而重新截短或随机删力度层。单份长录音与部署体积也需明确处理。
2. 按作者数值转换 `offset`、`tune`、`volume`、起音／衰减／保持／释放包络，以及松键录音的 `rt_decay`。当前引擎只有简单 `releaseAssetId`，并未实现作者的全部释放行为；不能默默忽略这些字段后宣称复现了原乐器。
3. 用真实键域、力度边界、短按与长按、保存重开、试听／波形／导出一致性验收适配结果，再切换默认钢琴与对应演示。用户不承担专业听审义务；需要主观判断的部分明确标注不确定性。
4. VCSL 本身不是当前全部传统管弦乐器的一对一替代库；后续逐套选择来源，不能声称所有现有乐器已经换库。
