# 内置资源维护流程

本文件是后续 AI 新增、替换或发布内置资源的操作入口。更新于 2026-11-07。实现细节见 [资源存储迁移交接](asset-storage-implementation.md)，普通开发命令见 [开发与部署](development.md)。遇到历史交接中的“音频直接提交 Git”“尚未外置”等描述，以本文件和当前实现为准。

## 两个仓库分别保存什么

- [BreezyMomo/MomoSoundForge](https://github.com/BreezyMomo/MomoSoundForge)：应用代码、构建和转换工具、来源与授权说明、采集 manifest、乐器映射、`sound-assets.lock.json`，以及需跟踪的生成目录 `src/data/builtin-catalog.json`。
- [BreezyMomo/MomoSoundForge-assets](https://github.com/BreezyMomo/MomoSoundForge-assets)：大型音频、带内嵌音频的工程／乐器资源和归档包存为 **Releases 附件**。该仓库的 Git 只保存少量说明，不把音频换一个 Git 仓库继续提交。

只改界面、代码或不改变音频依赖的说明，不需要发布新音频包。新增或修改大型内置资源时，需要协调资源 Release 和主仓库清单；不是每次开发都提交两个仓库。

主仓库于 2026-11-07 同名重建，保留了已经清除大型资源的提交历史；临时旧仓库 `MomoSoundForge-before-reset-20261107` 已删除。资源仓库和已发布的资源地址未变。不要重新合入历史清理前的分支，也不要因本机仍保有旧备份就将它们推回远端。

## 资源在本机和网站上的位置

- 制作候选：音频可以暂放在 `samples/<素材集合>/` 对应逻辑路径，来源、授权和映射也在该集合下维护。这里是制作输入，不代表文件应该进入 Git。
- 正式开发输入：`assets:sync` 按锁文件恢复到项目自己的 `.cache/sound-assets/`；可用 `SOUNDFORGE_ASSET_CACHE` 指定其他缓存。缓存内部按内容哈希和序号组织，不手动改缓存文件。
- 打包结果：`assets:pack --output` 指定的独立目录，不是自动上传区；不要放进待提交的源码目录。
- 运行资源：构建生成 `public/sound-library/`，再复制到 `dist/sound-library/`；均不提交 Git。当前浏览器仍从网站同源加载音频，**不是直接从资源仓库 Releases 播放**。
- 用户个人资源：用户在应用中保存入库时，写入其选择的本地文件夹中的 `index.json` 和 `resources/*.sfresource`。不会自动上传 GitHub，也不会自动成为内置资源。

`src/data/builtin-catalog.json`、固定框架包和已有的小型测试／教学示例是当前有意保留的跟踪项，不能按扩展名批量删除。新增大型内嵌音频示例应走资源外置流程，不能套用这个例外。

## 新增或替换资源的顺序

1. **核实来源与定义。** 登记许可、来源版本、原件与转换哈希；补齐实际音域、力度和演奏方式等有依据的映射。修改现有音色时区分资源内容修订与运输包版本，不静默改变已有作品的内嵌快照。
2. **接入构建输入。** 更新相关 manifest、转换／生成器和构建输入清单。新的素材集合目前需要检查 `tools/inventory-sound-assets.mjs` 和相应生成器，不是放一个 WAV 就会自动成为可选内置音源。保留既有逻辑 ID 和来源路径的含义，不能用缓存路径或下载 URL 充当身份。
3. **准备完整旧输入，再生成候选包。** 当前打包器会合并旧锁文件全部条目与工作区的新增／修改文件，需要先恢复 `archive` 配置（包含 build、audit 和 archive）。不要因为本地只下载了 build 包而丢掉旧归档。

   ```sh
   npm run assets:sync -- --profile archive
   npm run assets:pack -- --output <独立候选包目录> --version <新版本>
   ```

   `assets:pack` 只写资源包和候选 `sound-assets.lock.json`，不会上传、不会覆盖工程内锁文件，也没有“一键发布并更新主仓库”的能力。打包时同名工作区源文件优先；但构建解析已锁定路径时优先读取锁定缓存，所以修改旧 WAV 后必须重新打包并采用候选锁，不能据此假定构建已经使用新音频。

4. **在隔离检出中验证候选。** 将候选锁、对应元数据与代码作为同一组候选使用；通过 `assets:sync -- --profile archive --from <候选包目录>` 恢复，再运行下方检查。候选锁的 `urls` 初始为空，只适合显式本地恢复，不能作为远程可用清单直接发布主代码。
5. **在用户授权范围内发布资源。** 在资源仓库创建新的固定版本 Release，上传候选包和相应来源／校验说明。已发布附件不替换字节；包内容变化使用新版本、新哈希。不要删掉仍被旧锁文件引用的 Release。只编写文档或要求新增资源，不自动等同于授权 Git 提交、推送和公开发布。
6. **填写实际下载地址并验证远程恢复。** 将 Release 的实际 HTTPS 附件 URL 写入候选锁的 `urls`，不得使用 `latest`、开发机绝对路径或会漂移的地址。保持哈希和字节数不变；如附件字节变化，返回打包环节。使用空缓存、不带 `--from`，验证正式地址能够恢复；不能用已有缓存命中冒充远程下载验证。
7. **再提交主仓库的配套更新。** 在已取得提交／推送授权时，提交相匹配的锁文件、元数据、授权、映射、必要代码及重新生成的目录；音频包本体不进入暂存区。推送前确认新锁引用的附件已经可下载，避免 CI 引用不存在的资源。部署后检查真实网站的加载、试听、保存和导出。
8. **最后清理制作副本。** 确认原件、工作音频及所需归档已经进入可恢复的包并通过逐文件校验，再清理临时音频与验证目录。保留必要备份和验证报告，不先删掉唯一原件。

资源 Release 与代码提交不是原子事务。流程中断时，记录已上传的 Release、候选锁位置和已通过的检查；未验证完成前不要推进主干锁文件。若主代码需要回退，应一起回退锁文件、映射和目录，不能只换其中一项。

## 验证和提交前检查

候选隔离检出恢复 archive 输入后执行：

```sh
npm test
npm run assets:verify -- --profile archive
npm run test:assets
npm run test:provenance
npm run build
node tools/check-static-site.mjs
```

涉及声音内容时，检查代表性音符／力度、长短音、尾音和音域边界；试听、波形与导出使用同一渲染结果。保存后在没有素材网络服务的情况下验证已有音符可重放，不能把技术检查通过说成已完成全部主观听审。

**新增路径不一定被现有 `.gitignore` 覆盖。** 不使用未经检查的 `git add .`；用 `git status --short`、`git diff --cached --stat` 和 `git diff --cached --name-only` 检查实际暂存文件，尤其是音频、自包含工程、资源包、导出 ZIP 和生成目录。纯二进制目录可按目录忽略，混合目录只忽略应外置的文件，不能把授权和映射一起藏掉。

资源离开 Git 不会减少网站体积。2026-11-07 的完整网站约 951.4 MiB，已接近项目的静态站点预算；后续扩库必须运行体积检查，不能提高阈值来假装解决分发问题。独立音频分发、远程个人库和统一的一键发布命令尚未实现。

## 交接时必须留下的事实

- 哪些逻辑资源和内容修订改变了，哪些声音保持不变。
- 资源 Release 地址、候选／已采用锁文件、主代码提交，以及这些步骤是否真的完成。
- 执行过哪些本地、空缓存远程和浏览器验证；有哪些未验证项。
- 本地包、备份和必要报告的位置。机器路径只用于本地恢复说明，不写进可分发工程。

需要追溯历史清理与恢复时阅读 [Git 历史清理交接](git-history-cleanup.md)。此前临时缓存、重复打包、迁出原件和隔离验证工程已在 2026-11-07 核对后清理；不要假定历史日志中提到的每个临时目录仍存在，正常开发从当前锁文件重新恢复即可。
