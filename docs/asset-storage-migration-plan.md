## 开发基线与现有问题

- 最新产品结构为录音、合成器、乐器和音乐／音效。乐器保存音符绑定，用户导出的 `.sfresource` 和作品继续携带音源快照。开发用下载包只属于素材运输工具，不增加“乐器包”产品入口。
- 在较旧提交 `a24f5d0f7bc290a87425c18ba9a3e84d863878b8` 测得，受 Git 跟踪的文件原始大小合计约 2.257 GiB，`samples/` 约 2259.2 MiB。WAV 约 1922 MiB，`.soundforge` 约 275.5 MiB，`.sfinstrument` 约 91 MiB。开发时按最新分支重新盘点，不将这些数值当作远端仓库容量。
- `predev`、`pretest`、`prebuild` 目前依赖完整素材构建 `public/sound-library/`。构建器还读取部分内嵌音频的示例工程，因此仅迁走 WAV 会破坏构建。
- 部分乐器素材在构建时截取前 4 秒，最新资源列表又从乐器中提取独立录音。恢复完整尾音属于声音内容变更，应与存储迁移分开。
- 既有录音 ID 根据来源路径计算。移动本地存储位置时必须保留既有 ID 与原始来源字段，避免影响收藏、来源追踪和映射。

## 第一阶段确定的结构

代码仓库保存代码、元数据、许可证、采样映射、音符与处理配方、资源锁文件，以及少量测试素材。大文件存入独立资源仓库的 Releases，开发和 CI 通过同一清单恢复输入。

拟使用独立仓库 `BreezyMomo/MomoSoundForge-assets`。名称在实际创建时确认；该仓库的 Git 同样只保存少量说明与清单，大附件仅放 Releases。代码仓库重建不影响资源地址。锁文件记录实际发布后的地址，固定具体 release 与附件，禁止使用 `latest`。

第一阶段继续由构建器生成完整运行音库，浏览器保持当前同源按需加载。资源离开 Git 不自动减少 `dist/` 体积；对象存储、CDN 和用户可订阅的远程库另行安排。

### 资源分组

1. **构建输入**：隔离修订验收后，构建器实际读取的工作 WAV、自包含示例和必要辅助文件。原样打包，保持该活动库基线的声音与输出一致。
2. **原始归档**：完整原录音、原始资料与需保留的历史作品。独立备份并校验，默认开发同步不下载这些文件。
3. **可再生结果**：运行音库、试听音频、渲染报告、大型导出和压缩副本。后续由固定配方生成，输出目录忽略 Git。无法证明能重建的文件先作为归档保存。

原始归档再按用途标记 `audit`：来源校验依赖的原件、转换副本、网页快照、审核章节索引与隔离录音可显式同步，其余历史交付无需参与正常构建。恢复隔离录音用于校验，不改变隔离状态，不重新加入可用音库。

第一阶段继续跟踪小型生成目录 `src/data/builtin-catalog.json`，作为生成结果的明确例外；当前应用、AI 工具和离线测试会间接导入它。完整构建必须验证该目录与锁定输入、实际二进制内容一致，不允许目录与缓存各来自不同版本。

下载包按素材集合或乐器拆分，初期以约 100～300 MiB 为分包参考，单附件低于 GitHub Releases 的 2 GiB 限制。首轮包直接覆盖现有构建输入的依赖闭包，暂不重写全部加工流程。新附件使用新版本及新内容哈希；已有附件不替换字节。已经接入新锁文件和恢复工具的旧提交，仍能取得其锁定版本；迁移之前的提交需要单独的资源快照及恢复说明。

### 身份与内容校验

区分三个概念：稳定的逻辑资源 ID、具体内容的 SHA-256，以及下载地址。改名、换镜像、移动缓存不改变逻辑身份；改变录音或映射时产生新内容版本。

- 第一阶段保留当前资源 ID、原始 `sourcePath` 和兼容映射。缓存路径、下载 URL、资源包文件名均不参与 ID 计算。
- 同一录音被多个乐器使用时，可通过内容哈希复用存储；不同根音、增益、演奏方式等仍属于各自定义。不能仅因音频相同就合并用户资源身份。
- 新增 `sound-assets.lock.json`，使用独立的 `momo.sound-assets-lock/v1` 格式，不复用用户资源或本地库索引格式。
- 每包记录稳定包 ID、版本、用途、下载地址、压缩字节数、SHA-256、包内清单哈希、展开字节预算、文件数量上限；文件清单记录包内相对路径、字节数和 SHA-256。
- 清单保留来源版本、许可证及归档与工作副本的关系。采样率、声道、帧数等音频信息沿用采集 manifest，避免复制出两套可独立编辑的事实来源。
- 原始文件哈希、工作音频文件哈希与解码 PCM 哈希分别定义；计算 PCM 哈希时固定采样率、声道顺序、编码和字节序，不混用不同含义的哈希。
- 构建缓存依据锁文件、实际内容、配方、生成器及声音语义代码依赖失效。第一阶段可保守计算相关 `src/`、`tools/`、依赖锁文件、固定框架包及构建配置的内容指纹，避免手写依赖列表漏掉新增模块。mtime 可以辅助加速检查，不能单独决定正确性。缓存命中仍核对生成目录与输出内容。

### 本地同步与故障处理

新增 `tools/sound-assets.mjs` 命令入口，公共解析、缓存和解包逻辑放入 `tools/sound-asset-store.mjs`。建议提供：

- `npm run assets:pack`：从明确的输入清单生成本地待发布包和校验报告，不上传。
- `npm run assets:sync`：获取当前锁文件所需的构建输入，命中缓存则复用。支持显式本地包目录，便于发布前验收。
- `npm run assets:sync -- --profile audit`：额外恢复来源与转换校验需要的原始／审核文件。
- `npm run assets:verify`：离线核对锁文件、包及展开文件；完整素材缺失、截断、校验失败均以非零状态结束。
- `npm run assets:status`：说明需要哪些包、哪些已缓存、哪些损坏及修复方式。

默认缓存位于 Git 忽略的 `.cache/sound-assets/`，可由开发环境变量指定共享缓存；这些绝对路径不进入工程、资源定义或锁文件。解包结果按包内容哈希隔离，构建器通过解析器读取，不在源码目录回填一套会被误提交的 WAV。

镜像或本地包目录覆盖只改变取包位置，保持锁定哈希和内容验证。解析器区分逻辑相对路径与实际缓存路径：后者仅用于打开文件，生成 ID、basename、名称及来源元数据仍依据原逻辑路径。

下载写入临时文件，限制大小并验证整包哈希；解包前及过程中限制路径、数量与展开体积。拒绝绝对路径、路径越界、符号链接、重复目标及大小写冲突。逐文件校验成功后原子标记为可用，失败保留已有有效缓存。损坏缓存明确报错，在线同步可重新获取；离线模式不尝试网络访问。

构建、测试和普通开发启动不暗中下载。首次准备流程为 `npm ci`、`npm run assets:sync`，然后启动或构建。`npm run dev` 和 `npm run build` 缺素材时明确提示修复命令，禁止静默跳过资源或生成残缺音库。个人声音库不属于该同步器的读写范围。

实际改造覆盖主构建器的 manifest／示例读取、输入指纹及许可证复制，各 `builtin-instruments.mjs`、`builtin-game-sfx.mjs`、`builtin-nature-sfx.mjs` 的素材访问，以及完整音库／来源测试和对应验证工具。`audit-builtin-library.mjs` 与 `check-static-site.mjs` 继续检查真实生成目录。

构建输入依赖清单明确包括各采集 manifest、映射、许可证和示例索引、starter 配方指向的自包含工程、`forest-departure-8s.soundforge`、`exports/piano-window-light-20261104/piano-window-light.soundforge`、扩展乐器六个 demo，以及所有构建 job 引用的工作 WAV。文本若留在 Git，解析器从代码目录读取；外置项从受校验缓存读取。

## 测试与 CI 改造

### 离线测试

移除 `pretest` 对完整音库构建的强制依赖。将真正依赖完整素材的现有断言明确迁至音库集成测试，增加 `npm run test:assets`；不得根据文件是否存在而跳过断言。

另设 `npm run test:provenance`，明确要求 `audit` 输入，校验原始文件、来源资料、工作副本、转换及许可关系。现有 `gameSfx.test.mjs`、`natureSfx.test.mjs`、`builtinLevels.test.mjs` 中的原件、网页快照、历史工程、`review/chapters.json` 等断言按此职责拆分；`verify-orchestra-expansion.mjs` 所需正常／隔离录音原件和工作 WAV 一并纳入恢复清单。默认离线测试不替代这些校验。

`npm test` 使用少量真实 CC0 录音和合成测试数据，覆盖资源校验、映射、力度与轮替、渲染、导入导出和本地库行为。增加同步器测试，覆盖哈希错误、版本错误、离线缺失、超限下载、恶意归档、损坏缓存、重复同步和中断恢复。在线行为通过本地 HTTP 服务或模拟响应验证，不依赖公网音库。

测试夹具及其许可进入 Git。预算目标为全部音频夹具不超过 5 MiB；现有确有必要的夹具超出预算时单独说明，不通过删减功能覆盖来达标。

### 完整构建验收

现有 Pages 工作流按以下顺序调整：

1. 检出代码，安装锁定依赖，执行默认离线测试。
2. 恢复以锁文件内容哈希为 key 的素材缓存，运行 `assets:sync` 与 `assets:verify`。
3. 执行完整音库集成测试、生产构建及静态产物检查。
4. 既有 main 发布条件与权限沿用；实际推送或发布仍遵循用户指示。

缓存命中仍需验证清单与所需内容。缓存丢失时从固定版本包恢复，不能依赖 Actions 临时 artifact 作为唯一素材来源。完整构建不得退回下载上游最新素材。

首次迁移以及资源包更新必须额外执行 `audit` 同步和 `test:provenance`。普通代码变更执行默认离线测试、完整音库集成、构建和静态检查。缺少任何套件所要求的输入都明确失败。

## 分阶段交付

### 阶段零 盘点与备份

从最新分支枚举所有已跟踪二进制和内嵌音频，包含 `.sfresource`、`.soundforge`、`.sfinstrument`、ZIP、原始与工作 WAV。生成“保留在 Git、构建必需、原始归档、可再生”清单，使用文件校验判断重复，不能按扩展名直接删除。

分别保存“隔离前旧库”和“隔离修订验收后的活动库”两份基线，记录资源 ID、目录条目、生成文件及音频输出；存储迁移只与后者比较一致性。备份完整工作目录及 Git 引用，盘点所有相关 worktree，覆盖未推送代码、未跟踪配方、工程和导出；位于 Git 忽略目录的文件也需明确检查。Git bundle 不能覆盖这些未跟踪与忽略内容，需单独备份。

备份放在待清理仓库以外，并实际验证恢复。保留固定包和恢复工具的第二份离线副本，以及“迁移前 commit → 资源快照”的对应表和恢复说明。新增同步器不追溯修改旧提交。

### 阶段零补充 全部乐器初审与问题隔离

初审覆盖全部现有乐器及其录音，不限于钢琴。先保存旧音库的恢复基线，再形成计划继续使用的素材集合；完整旧集合进入兼容归档，不要求全部作为新默认音库发布。

自动检查覆盖每份录音和当前映射：解码、采样率、声道、时长、明显静音、满幅或异常电平、重复内容、缺失依赖、已知根音与来源记录、力度与演奏法覆盖，以及构建截取和实际播放时长。技术通过只代表对应规则通过，不能标为已完成主观音质验收。自动音高估计仅作线索，不覆写未经确认的根音。

对照试听按“来源套系、乐器、演奏方式”分组，不把不同来源的同名乐器合并验收。每组选择低、中、高实际录音根音，每个可用力度档取代表触发值；不存在的档位记录不适用，不强制补轻中重三档。全部映射接缝做自动选择检查，人工重点听变调跨度大、重叠、缺口等高风险边界两侧。

代表音高与力度下，固定种子连续触发交替录音至少两轮并记录顺序；其他组自动检查，疑点逐份试听。同时覆盖短按、长按、松键及尾音；确有循环或松键采样时验证对应行为。没有循环不能直接判为延音故障，one-shot 按其完整播放规则验收。作品窗口足够长，避免把父级裁切误判为源录音截断。同一案例可覆盖多个维度，无需把所有维度组合成一次穷举人工试听。

每个代表案例沿五个环节定位：原始文件独立原速解码、工作 WAV、应用内嵌 PCM、隔离单条映射的最小乐器工程、实际资源入口及作品。最小工程明确根音、力度、调音、释放和播放方式，移除额外效果及父级裁切；实际入口比较录音列表试听、乐器行试听、时间线与导出。记录异常首次出现的环节，再定位转换、构建、映射、渲染或作品处理问题。

保留原始电平试听；需要比较听感时另存试听副本并记录比较增益，不回写素材，不以逐份归一化后的结果判断力度关系。满幅采样、低电平或重复内容是复核线索，单个指标不直接等同于坏录音。

问题按原因记录：原始录音问题、转换或裁切问题、元数据或乐器绑定问题、播放器与处理链问题，以及待确认。多件乐器出现相似异常时优先检查共用处理链，避免将同一播放问题当作多个采样库失效。

每个条目标记保留、隔离或待确认，并另记是否继续默认提供及处置依据。待确认区分来源、听感、播放异常等具体原因；未逐份听审不是将现有条目全部撤下的依据。机器结论记录技术检查通过，代表性试听记录未发现异常，疑点记录异常待定位，已定处置记录已确认隔离，不以一个笼统的合格状态覆盖全部录音。

补充只读诊断入口 `tools/diagnose-instruments.mjs`：记录五环节对应关系、实际 region／asset、有效播放速率与增益、可用时长和截断位置。机器记录带 commit、工具版本、各阶段内容哈希、资源／映射 ID、音高、力度、时长与种子；人工记录案例、异常环节、判断依据、审核人、时间与未检查范围。报告写入独立忽略目录，不修改采集 manifest；小型结论与覆盖清单可入 Git，大型音频报告外置。

现有 `audit-builtin-library.mjs` 主要检查生成包、当前示例渲染和内嵌录音，不等于全量原件或全部演奏组合审查。`verify-orchestra-expansion.mjs` 会写包和报告，不能直接作为只读诊断入口；相关映射、渲染和编辑测试验证代码语义，不证明每套实际素材听感合格。

确认有问题的条目退出默认选择，原件与工作副本保留归档；同时分析它在乐器区域、松键采样、示例与目录中的反向引用。当前 `instrumentJobs` 按数量和体积分包，移除录音可能改变音区边界及其他目录 ID；`legacyInstrumentLevels` 的全组校准可能改变剩余录音增益；轮替数量改变会影响序列，内嵌示例也不会自动跟随 manifest 删除。

因此单独验收隔离修订，尽量保留原分包边界和校准参数，明确记录必须发生的重分包、增益、轮替、预览音符及示例变化。缺少可靠修复时可撤下整个受影响定义或示例，避免静默换声。保存旧生成包、原 ID 与退役状态、替代关系、反向引用及隔离前后数量和覆盖变化；不能让替代项静默冒充原资源。

更新固定数量断言及把源文件不存在作为拒收标准的测试，改为验证退出活动音库、剩余引用完整且归档按规则保留。隔离修订验收后冻结活动库基线，再开始存储迁移。播放或映射修复若会改变声音，同样作为独立改动验收，不混入纯存储搬迁。完整逐份听审留在后续批次，发现异常时扩大同来源、同转换批次或共用链路的检查范围。

### 阶段一 存储外置且声音不变

先开发本地打包、同步与校验，使用本地包完成一次完整恢复。经用户安排创建资源仓库并发布固定附件后，写入最终下载地址，再用公网地址验证干净环境。

改造 `tools/build-builtin-library.mjs`、`tools/builtin-instruments.mjs` 及其他实际读取素材的工具，通过资源解析器读取缓存。更新 `package.json`、`.gitignore`、测试和 Pages 工作流；新增 Git 跟踪文件检查，防止大音频、自包含导出和生成缓存重新入库。

声音迁移验收保留既有 ID、名称、采样范围、调音、增益、截取长度、轮替和播放语义。全量比较资源身份、映射参数、采样率、声道及内嵌 PCM 内容，再在相同工具链下比较代表性与高风险场景的渲染输出，并验证重复干净构建的稳定性。

若生成文件哈希仅因非声音元数据变化而不同，列出具体字段与原因。噪声种子、轮替顺序、截取长度等均属于声音语义，不纳入允许变化范围。

构建输入能够准确恢复后，才从 Git 跟踪集合移除已经迁出的文件。保留原始母带的校验归档；清理可再生输出前先验证生成路径。

### 阶段二 分批整理或替换各乐器音源

在第一阶段稳定后，根据全乐器初审清单逐批深入检查和修复录音来源、单音属性、原音高、录制力度、演奏方式、交替组、音准及尾音。信息不足时保留未知，不根据文件名补造事实。新增素材先进入候选集合，完成所需技术检查和试听后才加入默认音库。

原件正常且异常发生在转换、裁切、映射或播放链时优先修对应环节；少量有缺陷的音符或力度档可局部补换。只有代表性检查发现广泛原始缺陷、素材类型不符合目标、来源依据或整套音色一致性不足且补修成本较高时，才考虑替换同一套素材。新候选先核对来源版本及哈希，重复下载同一版本同一字节不能修复播放器问题。

首批可取约 6～12 份有代表性的候选，覆盖三个音区及实际存在的力度或交替录音；数量依素材结构调整，不强行凑档。完成五环节对照、映射边界、尾音、预算与便携导出验证后再扩大采集。

区分原始录制力度与乐器触发范围；单层、多层素材共存，不强制轻中重三档。完整录音、为演奏截取的片段和试听结果各有明确身份与用途，独立录音不再隐含宣称是完整原件。

根据问题明确程度与可靠素材的可获得性，选择一种或少量乐器验证修复及入库流程，钢琴仅作为可选试点。每套乐器优先使用来源一致的素材整理可用音区与映射，检查相邻音符、力度切换、重复触发及尾音。保留现有预算，按实际试听决定需要的层数和音区，不能直接把所有录音装入一个超预算定义。流程通过后按全乐器清单继续处理，其余乐器不能因试点通过而标记已验收。

恢复完整录音、修正音高、增益或映射均按内容更新发布新版本，原作品快照不联动。再逐步把加工 WAV、自包含示例与试听转为“固定原件加配方”，避免重复保存可再生音频。

第二阶段预计调整 `tools/build-builtin-library.mjs`、`src/builtinLibrary.ts`、`src/recordingSources.ts`、`src/SoundLibrary.tsx` 和资源包装路径：目录携带实际资源修订，加载及 `resourceFromDefinition` 等包装流程保留修订号，不再一律产生 `version: 1`。资源修订与 Releases 包版本分别管理。

完整录音提供独立加载入口，避免为了试听一份录音先加载父乐器并从中提取。`recordingSources.ts` 的映射汇总仅描述映射，不作为录制力度的事实来源。同步修正文案和测试，已有自包含工程及个人库保持快照语义。

完整钢琴按需加载已先行落地，见 [完整钢琴接入交接](vcsl-piano-integration.md)：A0–C8 全音域轻量引用，当前音符依赖仍受 24 MiB PCM 预算约束；普通内嵌资产上限 64，含引用的字典上限 512。此实现不是流式网络读取；资源包、锁文件与远程存储属于后续单独完成的存储工作，Git 历史迁移尚未执行。

### 阶段三 Git 历史重建与后续入库

完成资源恢复、备份验收并锁定当时已经接受的资产版本后，即可单独安排 Git 历史重建，不必等全部乐器逐份听审或阶段二所有批次结束。操作前复核完整备份、当前代码、未推送工作、分支及标签；新历史仅纳入轻量源码、清单、配方、许可与测试夹具。

优先保留现有代码仓库地址与 GitHub 设置。若需要更换仓库，另行列明 CI、Pages、链接和本地 remote 的迁移；资源仓库与资源 URL保持稳定。旧大文件不能通过残留分支或标签再次进入新历史。备份旧历史不放回新代码仓库。

历史重写、强制推送、删除仓库或旧标签均属于单独操作，本方案不执行。目标验收以全新 clone 的可达对象和跟踪文件为准，不能只观察原工作区的 `.git` 是否立即缩小。

之后新增音源统一使用同一流程：来源许可登记、内容校验、音频信息核实、试听筛选、独立资源包发布、锁文件更新、完整构建验证。

## 文件范围与验收条件

预计新增 `sound-assets.lock.json`、`tools/sound-assets.mjs`、`tools/sound-asset-store.mjs`、`tools/check-resource-policy.mjs`、`tools/diagnose-instruments.mjs`、同步器／诊断测试及少量真实夹具；完整音库与来源测试单独组织。更新 `package.json`、Vitest 配置、`.gitignore`、构建器、素材工具、`.github/workflows/pages.yml` 和开发／素材维护说明。具体改名可遵循最新分支既有结构，协议与职责保持上述约定。

第一阶段验收必须同时满足：

- 干净检出安装依赖后，`npm test` 无音库缓存、无公网仍可通过；完整素材测试未被静默跳过。
- 从固定本地包和正式下载地址分别恢复过一次；恢复结果文件数量、字节数和 SHA-256 一致。
- 相同输入重复同步不重下大包，损坏或缺失缓存明确失败并可恢复。
- `npm run test:assets`、`npm run test:provenance`、`npm run build` 与静态站点检查通过；基线资源全量核对，并验证代表性与高风险场景渲染一致。
- 真实浏览器走通独立录音试听、乐器选源、写音符、保存重开、资源导出再导入及音频导出；保存后的工程断开素材服务仍可独立使用。
- Git 跟踪集合中没有迁出的音频、内嵌大音频副本、缓存或大型生成结果；小型 `src/data/builtin-catalog.json`、必要测试夹具和固定框架包为明确例外。首轮目标为全部跟踪文件原始大小低于 30 MiB；任何额外例外明确列出。
- 迁移没有修改个人本地库、已有作品快照或音频引擎语义。资源和工程预算继续生效。

## 后续范围

本次第一阶段不实现浏览器直接从 Releases 获取音源、不实现用户远程库订阅、CDN、全局用户资源存储去重、全部乐器重做或大规模新音源采集。Git LFS 不作为默认存储方案。

GitHub Pages 的 1 GB 站点上限仍适用。需要扩大线上音库时，再基于当前资源身份与校验机制增加对象存储和 CDN，单独处理跨域、缓存与可用性。
